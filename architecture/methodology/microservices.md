# Микросервисная архитектура (Microservices)

## Определение

Микросервисная архитектура — стиль, при котором приложение строится как набор небольших независимых сервисов, каждый из
которых работает в собственном процессе, владеет своей базой данных и общается с другими сервисами по сети (HTTP, gRPC,
очереди сообщений). Каждый сервис реализует конкретную бизнес-функциональность и может быть развёрнут, масштабирован и
обновлён независимо.

## Подробности

Микросервисы — не серебряная пуля и не «следующий шаг эволюции после монолита». Это архитектурный выбор, который решает
конкретные проблемы: масштабирование команд и организации, независимость деплоев, изоляция отказов.

**Контраст с монолитом**:
- Монолит: один процесс, одна БД, деплой всего приложения при любом изменении.
- Микросервисы: N процессов, каждая со своей БД, деплой только изменённого сервиса.

**Ключевые принципы** (не все должны выполняться одновременно):
- **Разделение по бизнес-возможностям** — границы сервисов проводятся по Bounded Contexts (DDD), а не по техническим слоям.
- **Децентрализованные данные** — у каждого сервиса своя БД (Polyglot Persistence). Нет общей схемы.
- **Умные endpoints, глупые каналы** — логика в сервисах, коммуникация через простые протоколы (REST, события).
- **Инфраструктурная автоматизация** — CI/CD, контейнеризация, оркестрация (Kubernetes) — без этого микросервисы
превращаются в кошмар.
- **Design for Failure** — Circuit Breaker, ретраи, Health Checks, Graceful Degradation.

**Коммуникация между сервисами**:
- Синхронная: HTTP/REST, gRPC. Просто, но создаёт цепочки зависимостей.
- Асинхронная: RabbitMQ, Kafka, AWS SQS/SNS. Слабая связанность, но eventual consistency.

## Плюсы

- **Независимое масштабирование** — нагруженный сервис масштабируется отдельно.
- **Изоляция отказов** — падение сервиса каталога не кладёт сервис заказов.
- **Независимые деплои** — быстрее delivery, меньше риск релиза.
- **Свобода технологий** — Python для ML, Go для высоконагруженных, Node.js для API.
- **Согласование с командами** — команда владеет сервисом целиком (you build it, you run it).

## Минусы

- **Распределённая сложность** — сеть ненадёжна: latency, ошибки, дубликаты, таймауты.
- **Eventual consistency** — нельзя сделать `BEGIN TRANSACTION` через 5 сервисов.
- **Операционная сложность** — мониторинг, трейсинг, логирование, деплой, дебаг распределённой системы.
- **Стоимость** — больше инфраструктуры, больше человеко-часов на поддержку.
- **Не подходит для стартапов** — преждевременное разбиение на микросервисы убивает скорость.

## Когда применять

- Команда выросла настолько, что монолит стал узким местом (десятки разработчиков).
- Разные части системы имеют разные требования к масштабированию и доступности.
- Нужна организационная автономия (каждая команда может деплоить независимо).

```
│  (PG)    │    │  (PG)    │    │  (MongoDB)  │

              └─────────────┘
```
