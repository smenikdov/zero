# Распределённый монолит (Distributed Monolith)

## Определение

Распределённый монолит — система, которая структурно разбита на «микросервисы» (отдельные процессы, контейнеры), но не
обладает ключевыми свойствами микросервисной архитектуры: независимым деплоем, изолированными данными, слабой
связанностью. Сервисы нельзя деплоить по отдельности, они разделяют базу данных, и изменение одного неизбежно требует
изменения других.

## Подробности

Распределённый монолит — худшее из двух миров:
- От монолита: сильная связанность, скоординированные деплои, отсутствие изоляции.
- От микросервисов: сложность распределённых систем (сеть, latency, отладка, мониторинг).

Как система приходит к этому состоянию:

1. **Общая база данных** — все сервисы читают/пишут в одну БД. Изменение схемы ломает все сервисы одновременно.
2. **Цепочки синхронных вызовов** — A вызывает B, B вызывает C, C вызывает D. Отказ D → каскадный отказ всей цепочки.
3. **Shared библиотеки** — общий код (модели, утилиты, конфиги) в отдельном пакете, который подключают все сервисы.
Изменение пакета → тотальный ребилд и передеплой всех сервисов.
4. **Скоординированные деплои** — сервисы имеют неявные контракты, нарушение которых требует одновременного деплоя
нескольких сервисов.
5. **Разбиение по техническим слоям, а не по бизнес-возможностям** — «сервис контроллеров», «сервис репозиториев», «сервис вьюх».

## Почему это проблема

- **Хрупкость** — одна миграция БД ломает 10 сервисов.
- **Деплой — кошмар** — нужно деплоить несколько сервисов в правильном порядке, а rollback — отдельный проект.
- **Отладка — пытка** — трассировка запроса через 7 сервисов, 3 очереди и общую БД.
- **Дороже и монолита, и микросервисов** — инфраструктурные затраты как у микросервисов, связанность как у плохого монолита.
- **Нет преимуществ микросервисов** — нельзя масштабировать независимо, нет изоляции отказов.

## Как избежать

1. **Начинать с монолита** — и выделять микросервисы только когда возникает реальная потребность.
2. **Database per Service** — каждый сервис владеет своей схемой/БД. Доступ к данным только через API сервиса.
3. **Асинхронная интеграция** — события и очереди вместо синхронных цепочек HTTP-вызовов.
4. **Чёткие контракты** — API сервиса как публичный интерфейс; менять контракт — мажорный релиз.
5. **Bounded Context** — границы сервисов должны совпадать с границами домена.

## Схема

```
❌ Distributed Monolith               ✅ Правильные микросервисы

 ┌─────────┐ ┌─────────┐             ┌─────────┐ ┌─────────┐
 │ Service │ │ Service │             │ Orders  │ │ Catalog │
 │    A    │─┤    B    │             │  (PG)   │ │(MongoDB)│
 └────┬────┘ └────┬────┘             └────┬────┘ └────┬────┘
      │           │                      │           │
      └─────┬─────┘                   REST API     REST API
            │                            │           │
    ┌───────┴───────┐              ┌─────┴───────────┴─────┐
    │  ОДНА БД      │              │  События (Kafka/Rabbit)│
    │  (shared)     │              └────────────────────────┘
    └───────────────┘
```
