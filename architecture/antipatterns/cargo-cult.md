# Карго-культ (Cargo Cult)

## Определение

Карго-культ в программировании — слепое копирование практик, инструментов и архитектурных решений без понимания их
смысла и контекста. Термин происходит от антропологии: после Второй мировой войны жители тихоокеанских островов строили
«посадочные полосы» из кокосовых пальм, имитируя действия военных, которые привозили грузы (cargo), не понимая, как
работает авиация.

## Подробности

В мире разработки карго-культ проявляется повсеместно:

- **Архитектура**: команда выбирает микросервисы, потому что «так делают Netflix и Uber», не имея ни масштаба, ни
распределённой команды.
- **Технологии**: внедрение Kubernetes для приложения с 100 пользователями; выбор React просто потому, что это «модно».
- **Методологии**: внедрение Scrum с ежедневными стендапами, спринтами и story points, но без главного — инспекции и
адаптации процессов.
- **Паттерны**: использование CQRS, Event Sourcing, Saga в простом CRUD-приложении, потому что «в докладах круто выглядит».

Карго-культ отличается от осознанного заимствования тем, что отсутствует анализ: какую проблему это решает именно у нас?
Какие недостатки? Каковы альтернативы? Команда просто имитирует «правильный» процесс или архитектуру, надеясь, что успех
последует автоматически.

## Почему это проблема

- **Неоправданная сложность** — архитектура становится дороже в поддержке, чем того требует задача.
- **Замедление разработки** — время тратится на ненужные абстракции и инфраструктуру.
- **Разочарование команды** — когда «модная» технология не приносит обещанных результатов, винят технологию, а не
решение её использовать.
- **Повышение порога входа** — новые разработчики вынуждены изучать сложный стек, не понимая его ценности.

## Как избежать

1. **Начинайте с проблемы, а не с решения.** Прежде чем выбрать технологию или архитектуру, ясно сформулируйте, какую
проблему вы решаете.
2. **Используйте контекстный анализ.** Почему это сработало у тех, на кого вы ссылаетесь? Каковы были их условия? Похожи ли ваши?
3. **Идите от простого к сложному.** Монолит → модульный монолит → микросервисы — только когда масштаб и команда требуют.
4. **Экспериментируйте с proof-of-concept.** Проверьте гипотезу на маленьком изолированном проекте, прежде чем влиять на
всю систему.
5. **Задавайте «почему» пять раз.** Техника «5 Whys» помогает отличить реальную потребность от модного тренда.

## Пример

```js
// ❌ Карго-культ: CQRS + Event Sourcing + Saga для заметок
class NoteAggregate {
  createNote(title, content) {
    return [{ type: "NoteCreated", title, content, timestamp: Date.now() }];
  }
}

class NoteProjector {
  #notes = [];
  apply(event) {
    if (event.type === "NoteCreated") {
      this.#notes.push({ title: event.title, content: event.content });
    }
  }
  getNotes() { return this.#notes; }
}

// Проблема: обычный CRUD, а архитектура как в банковской системе
// 3 дополнительных абстракции только для создания заметки

// ✅ Простое решение, соразмерное задаче
class NoteService {
  #notes = [];
  create(title, content) {
    const note = { id: this.#notes.length + 1, title, content };
    this.#notes.push(note);
    return note;
  }
  getAll() { return this.#notes; }
}
```
