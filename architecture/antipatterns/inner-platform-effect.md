# Эффект внутренней платформы (Inner-Platform Effect)

## Определение

Inner-Platform Effect — антипаттерн, при котором команда разработки создаёт внутри системы настраиваемую «платформу» или
«движок», который настолько усложняется, что становится пародией на ту платформу, поверх которой он построен.
Разработчики тратят ресурсы на создание собственной версии того, что уже предоставляет среда исполнения, фреймворк или
инструмент.

## Подробности

Термин появился в мире корпоративного ПО: компания покупает ERP-систему, а затем допиливает её «конструктором отчётов»,
«гибкой системой прав», «своим языком описания бизнес-процессов». Через пару лет конструктор становится сложнее самой
ERP, а команда поддерживает внутреннюю «платформу», а не бизнес-функциональность.

Формы проявления:
- **Самописный ORM** вместо Sequelize/Prisma.
- **Собственный язык конфигурации** (DSL), который обрастает условиями, циклами, переменными → становится плохим языком
программирования.
- **Rule Engine для бизнес-правил** — JSON/YAML с eval-подобным интерпретатором.
- **Универсальный компонент** в UI, который через пропсы настраивается на все случаи жизни (200+ пропсов, 50+ условных рендеров).
- **Фреймворк для фреймворка** — команда пишет обёртку над React/Vue/Angular, которая превращается в собственный фреймворк.

Драйверы эффекта:
- **Синдром «Not Invented Here» (NIH)** — «мы сделаем лучше».
- **Желание «гибкости»** — кажется, что свой инструмент будет более настраиваемым.
- **Недооценка сложности** — создание качественного инструмента требует на порядки больше усилий, чем кажется.

## Почему это проблема

- **Растрата ресурсов** — команда годами поддерживает внутреннюю платформу, которая не даёт бизнес-ценности.
- **Хуже, чем готовое** — самописный аналог всегда уступает зрелым open-source решениям.
- **Нет документации и сообщества** — обучение новых разработчиков — месяцы; ошибки гуглятся в Slack, а не на StackOverflow.
- **Lock-in хуже вендорского** — вендора можно сменить, внутреннюю платформу — нет (её авторы давно уволились).

## Как избежать

- **Оценить зрелые open-source решения** — часто они уже делают то, что вам нужно.
- **Правило «Integrate, don't reinvent»** — покупай/интегрируй готовое, а не строй своё.
- **Чётко определить границы** — если пишете DSL, ограничьте его простым подмножеством, не создавайте язык.
- **Регулярно пересматривать** — если внутренний инструмент сложнее задачи, которую он решает, — это красный флаг.

## Примеры

```
❌ Внутренняя платформа:

1. Самописный DI-контейнер с XML-конфигурацией
   Вместо: Awilix, InversifyJS, tsyringe

2. Собственный HTTP-роутер с middleware-системой
   Вместо: Express, Fastify, Koa, Hono

3. DSL для бизнес-правил на JSON:
   {
     "when": { "field": "status", "is": "shipped" },
     "and": { "field": "paid", "equals": true },
     "then": [{ "action": "sendEmail", "template": "shipped" }]
   }
   → Через год: циклы, переменные, вызовы других правил
   → Стало хуже, чем просто код на JS

4. UI-компонент «на все случаи жизни»:
   <UniversalTable
     data={items}
     columns={columns}
     sorting={{ multi: true, defaultSort: [...] }}
     filtering={{ serverSide: true, debounceMs: 300 }}
     pagination={{ type: "infinite-scroll", pageSize: 20 }}
     selection={{ mode: "multi", onSelect: fn }}
     rowActions={[{ icon, label, action, condition }]}
     expandableRow={renderer}
     grouping={{ by: "category", collapsible: true }}
     // ... ещё 50 пропсов
   />
   → Поддерживать этот компонент сложнее, чем написать таблицу для каждого случая

✅ Здоровая альтернатива:
- Использовать готовую библиотеку таблиц (TanStack Table)
- Бизнес-правила писать на том же языке, что и остальной код
- DSL только там, где конфигурация действительно нужна непрограммистам
```
