# Золотой молоток (Golden Hammer)

## Определение

Golden Hammer (Золотой молоток) — антипаттерн, при котором знакомая и/или модная технология, инструмент или
архитектурный стиль применяется ко всем задачам без анализа альтернатив. «Если у тебя в руках молоток, всё вокруг
выглядит как гвоздь».

## Подробности

Термин введён в книге AntiPatterns (Brown et al., 1998). Корень проблемы — не в самой технологии (она может быть
отличной), а в её бездумном применении там, где она не подходит.

Проявления золотого молотка:

- **Базы данных** — «Всё кладём в MongoDB» (даже реляционные данные с жёсткими связями и транзакциями).
- **Микросервисы** — разбиение на микросервисы ради микросервисов, даже для CRUD-сайта с 3 эндпоинтами.
- **Фреймворки** — «React на всё»: лендинг из 3 блоков, простая админка, статический сайт — всё на тяжёлом SPA-фреймворке.
- **Языки** — писать всё на одном языке просто потому, что команда знает только его, даже когда задача очевидно под другой язык.
- **Фанатизм методологий** — слепое следование Scrum, TDD, DDD даже там, где они мешают.

Почему это происходит:
- **Эффект IKEA** — мы ценим то, во что вложили усилия на изучение.
- **FOMO (Fear Of Missing Out)** — технология на хайпе, «все её используют».
- **Комфортная зона** — знакомая технология = предсказуемый результат (в краткосрочной перспективе).

## Почему это проблема

- **Завышенная стоимость и сложность** — микросервисы для простого блога: оркестрация, мониторинг, сетевые задержки.
- **Плохие компромиссы** — MongoDB для финансовых транзакций: потеря ACID, сложные запросы с $lookup вместо JOIN.
- **Блокировка инноваций** — команда не изучает альтернативы, пропуская лучшие инструменты.
- **Выгорание** — борьба с инструментом, который не подходит для задачи.

## Как избежать

- **Анализ перед выбором** — для каждой задачи оценивать минимум 2-3 альтернативы с плюсами/минусами.
- **Правило «подходящего инструмента»** — технология решает проблему, а не проблема подгоняется под технологию.
- **Architecture Decision Records (ADR)** — документировать решение: контекст, альтернативы, почему выбрано X.
- **Stay hungry, stay foolish** — изучать новые инструменты, даже если текущий «работает».

## Примеры (концептуально)

```js
// ❌ Золотой молоток: микросервисы для TODO-приложения
// Каждый из этих сервисов — отдельный деплой, БД, мониторинг
//
// ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
// │ todo-svc │  │ user-svc │  │ auth-svc │  │ stats-svc│
// └──────────┘  └──────────┘  └──────────┘  └──────────┘
//      4 БД, 4 CI/CD пайплайна, Kafka для коммуникации
//      Всё это для 200 активных пользователей

// ✅ Модульный монолит для той же задачи
// modules/
//   todos/    — CRUD задач
//   users/    — управление пользователями
//   auth/     — аутентификация
//   stats/    — статистика
// Одна БД, один деплой, внутрипроцессные вызовы
// Масштабирование — когда (и если) потребуется.
```
