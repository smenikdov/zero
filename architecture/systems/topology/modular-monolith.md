# Модульный монолит (Modular Monolith)

## Определение

Модульный монолит — топология, при которой система по-прежнему разворачивается как один процесс и один артефакт, но
внутри жёстко разделена на модули с явными границами и публичными API. Модули общаются через контракты (и при желании
внутрипроцессные события), а не через свободный доступ к чужим деталям реализации.

## Подробности

Это компромисс между «простым» монолитом и микросервисами:
- как у **монолита** — один деплой, одна (или логически разделённая) БД, вызовы без сети, простые транзакции;
- как у **микросервисов** — модули по бизнес-возможностям, изоляция через API, возможность позже вынести модуль в сервис.

**Ключевые правила**:
- **Границы по домену** — модули режутся по Bounded Context / бизнес-возможностям, не по техническим слоям.
- **Только публичный API** — чужой внутренний код и таблицы модуля недоступны напрямую.
- **Слабая связанность внутри процесса** — предпочтительны интерфейсы и события, а не «достать чужой репозиторий».
- **Готовность к выносу** — контракт модуля должен позволять заменить in-process вызов на HTTP/gRPC без переписывания
вызывающей стороны.

## Плюсы

- **Простота эксплуатации** — один процесс, один деплой, локальный запуск.
- **Производительность и транзакции** — без сетевых hops и распределённых saga «из коробки».
- **Порядок в коде** — границы модулей сдерживают Big Ball of Mud.
- **Эволюционный путь** — модуль можно позже выделить в микросервис.

## Минусы

- **Общий деплой** — изменение одного модуля всё равно релизуется вместе со всеми.
- **Общее масштабирование** — нельзя масштабировать только «горячий» модуль как отдельный сервис.
- **Дисциплина** — без code review и архитектурных правил границы размываются.
- **Общая инфраструктура** — один рантайм, часто одна БД; сбой процесса валит всё приложение.

## Когда применять

- Система уже не «маленький CRUD», но рано платить ценой микросервисов.
- Команда растёт, нужны явные владельцы областей кода.
- Важны ACID и скорость разработки, но нужна модульность «на вырост».
- Планируется возможный переход к микросервисам без большого rewrite.
