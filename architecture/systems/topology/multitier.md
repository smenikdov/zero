# Многоуровневая архитектура (Multitier / N-tier)

## Определение

Многоуровневая архитектура (Multitier, N-tier) — архитектурный стиль, в котором система физически разделяется на
уровни (tiers): отдельные процессы, хосты или сетевые узлы. Классический пример — 3-tier: клиент, сервер приложений,
база данных. Уровни общаются по сети (или через IPC), а не только через вызовы функций в одном процессе.

## Подробности

Уровни — это **физическая** топология развёртывания. Их не следует путать со слоями (layers): слои описывают логическую
организацию кода, уровни — где этот код реально выполняется.

Один уровень может содержать несколько логических слоёв. Например, на сервере приложений часто живут и Presentation
(API), и Business. И наоборот: один логический слой можно разнести по нескольким уровням.

**Типичные варианты**:

1. **1-tier** — всё на одной машине/в одном процессе (десктопное приложение с локальной БД).
2. **2-tier** — клиент + сервер данных (толстый клиент напрямую к БД).
3. **3-tier** — Presentation (браузер/клиент) → Application Server → Database Server.
4. **N-tier** — дополнительные уровни: API gateway, кэш, очереди, read-replicas, CDN.

**Связь с другими стилями**:
- **Monolith** часто деплоится как 3-tier: SPA/клиент + один application-процесс + БД.
- **Microservices** — это N-tier (и больше) с множеством application-уровней по бизнес-границам.
- **Layered** отвечает на вопрос «как разрезать код», Multitier — «как разместить и связать узлы».

## Плюсы

- **Независимое масштабирование уровней** — можно усилить только application-tier или только БД.
- **Изоляция** — падение/перегрузка одного уровня не всегда валит всю систему целиком.
- **Безопасность** — БД можно спрятать во внутренней сети, наружу отдать только presentation/API.
- **Специализация инфраструктуры** — разные уровни на разном железе и с разной конфигурацией.

## Минусы

- **Сетевая сложность** — latency, сериализация, частичные отказы, ретраи.
- **Операционные затраты** — деплой, мониторинг и отладка распределённой цепочки.
- **Согласованность** — транзакции через уровни сложнее, чем внутри одного процесса.
- **Overkill для простых систем** — лишние hops без реальной нагрузки.

## Когда применять

- Веб- и корпоративные системы, где клиент, логика и данные должны жить раздельно.
- Когда нужна изоляция БД от публичной сети.
- Когда уровни масштабируются по-разному (много чтения UI, тяжёлая запись в БД).
- Как базовая топология до (или вместо) перехода к микросервисам.

## Схема

```
┌──────────────┐     HTTP      ┌──────────────────┐     SQL      ┌──────────┐
│  Client tier │ ────────────► │ Application tier │ ──────────► │ Data tier│
│ (browser/app)│               │  (API / services)│             │   (DB)   │
└──────────────┘               └──────────────────┘             └──────────┘
```
